# Pi lanes, ownership, subagents, and context windows

## Scope and provenance

This compares the three OpenSrc `main` exports: upstream [`earendil-works/pi`](https://github.com/earendil-works/pi), [`fitchmultz/pi`](https://github.com/fitchmultz/pi), and [`fitchmultz/pi-posthorse`](https://github.com/fitchmultz/pi-posthorse). OpenSrc records them as fetched on 2026-09-05, but the exports contain no `.git` metadata or commit SHA, so their exact commits cannot be identified. Their package metadata reports Pi `0.85.1` in both Pi trees ([upstream agent package](https://github.com/earendil-works/pi/blob/main/packages/agent/package.json), [fork agent package](https://github.com/fitchmultz/pi/blob/main/packages/agent/package.json)) and Posthorse `0.4.4` ([package](https://github.com/fitchmultz/pi-posthorse/blob/main/package.json)). The only exact source revision available is Posthorse's tested fork baseline, [`f9b06177e565f70cd243a785d088d1c491830dbd`](https://github.com/fitchmultz/pi/commit/f9b06177e565f70cd243a785d088d1c491830dbd), identified as Pi `0.85.0` ([requirements](https://github.com/fitchmultz/pi-posthorse/blob/main/README.md#requirements)).

## What is shipped, and at what layer

### General lanes: shipped in agent core, not native delegated subagents

`@earendil-works/pi-agent-core` `0.85.1` exports `AgentHarness` and its session APIs from the package root ([package](https://github.com/earendil-works/pi/blob/main/packages/agent/package.json), [exports](https://github.com/earendil-works/pi/blob/main/packages/agent/src/index.ts)). Its current implementation has real durable acceptance/drive/recovery, tool execution, Memory/JSONL/SQLite backends, and runtime tests ([specification/status](https://github.com/earendil-works/pi/blob/main/packages/agent/docs/harness.md#09-implementation-status), [runtime test](https://github.com/earendil-works/pi/blob/main/packages/agent/test/harness/runtime/harness.test.ts)). Thus the `0.84.0` changelog's “compile-complete scaffold” warning is historical, not a correct description of the inspected `0.85.1` tree; that same release promoted the lane-based v4 `Session`, `SessionStorage`, `SessionRepo`, and `AgentHarness` to default exports ([changelog](https://github.com/earendil-works/pi/blob/main/packages/agent/CHANGELOG.md#0840---2026-08-06)). It is not entirely finished: `watchSession` is the sole stubbed harness method, and JSONL snapshot compaction, remote-session transport, search, telemetry, parts of fork transfer, and precise rewrite remain incomplete or design-only ([status](https://github.com/earendil-works/pi/blob/main/packages/agent/docs/harness.md#09-implementation-status)).

A lane is a **general execution branch inside one durable Session**: a named tree tip plus model/tool configuration, queues, and at most one operation. There is no implicit `main`; multiple lanes can share the immutable entry tree and run independent work, while all mutations serialize on one Session mutation line ([branches and lanes](https://github.com/earendil-works/pi/blob/main/packages/agent/docs/harness.md#23-branches-and-agentlanes), [mutation line](https://github.com/earendil-works/pi/blob/main/packages/agent/docs/harness.md#43-the-session-mutation-line)). Nothing in this abstraction means “delegate to another agent,” creates a child session, or assigns a different process.

This is also not yet the ordinary coding-agent CLI's lane UX. `@earendil-works/pi-coding-agent` `0.85.1` still composes `AgentSession` with the legacy `SessionManager` in its normal entry point ([main](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/main.ts)); its package explicitly excludes `dist/client`, `dist/experimental`, and `dist/cli/experimental`, after `0.85.0` accidentally published internal experimental code ([package files](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/package.json), [0.85.1 fix](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/CHANGELOG.md#0851---2026-09-05)). Verdict: lanes are a shipped core-library runtime, but remote/session-worker hosting and a stock end-user lane workflow remain source-only or absent.

### Session ownership: an operational precondition, not a distributed lock

The ownership guarantee is exactly one host-assigned writable owner for an entire Session. While attached, the harness keeps the authoritative process-local projection for each lane, and one live `Drive` advances a lane's operation. Lanes solve workloads that resemble multi-writer activity without allowing multiple Session writers ([non-goals](https://github.com/earendil-works/pi/blob/main/packages/agent/docs/harness.md#06-non-goals), [live operation task](https://github.com/earendil-works/pi/blob/main/packages/agent/docs/harness.md#41-the-live-operation-task)).

That guarantee is **not enforced across processes by storage**. The SQLite backend rejects overlapping handles it owns in one process but has no lease, lock, fence, heartbeat, or takeover; opening the same Session for writes in another process is unsupported and host lifecycle must prevent it ([SQLite backend README](https://github.com/earendil-works/pi/blob/main/packages/session-backends/sqlite-node/README.md)). Therefore “a lane per worker” is unsafe unless one Session-owning host mediates every mutation; writable administration also requires exclusive ownership (read-only listing and fork snapshots are explicit exceptions).

### Stock subagents: a manually installed process-spawning example

Upstream's subagent facility is an optional example extension included under `examples`, not a built-in delegated-session API. Its installation instructions require symlinking it into the user's extension directory, and it describes each subagent as a separate Pi process ([README](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/subagent/README.md)). The implementation spawns `pi --mode json -p --no-session`, optionally in parallel, and inherits/configures model, thinking level, and tools ([source](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/subagent/index.ts)). These subprocesses have isolated provider context and no persisted Pi session because of `--no-session`. They are neither lanes nor durable child sessions, and no lane/session ownership is delegated to them.

### Append-only provider context: a lane invariant, not provider-side state

The durable harness specifies that, between requests on one lane, model context grows only at the tail: mid-run writes defer to checkpoints so they append after the prior tail; compaction is the deliberate invalidation ([context projection](https://github.com/earendil-works/pi/blob/main/packages/agent/docs/harness.md#25-branch-queries-and-context)). Provider calls receive a stable cache-affinity identity, `${sessionId}:${laneName}` ([generation source](https://github.com/earendil-works/pi/blob/main/packages/agent/src/harness/runtime/drive/generation.ts)). This is useful for provider prefix caching, but it does **not** mean Pi relies on a provider-owned conversation: Pi reconstructs and sends the projected messages, and compaction replaces the active prefix. It is a trusted contract rather than a provider guarantee—an application hook can transform context—and it is not a blanket property of the older `Agent`/ordinary coding-agent path, whose documented `transformContext` can prune or inject messages before every request ([agent README](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md#message-flow)).

## Fork and Posthorse context-window policy

The inspected `fitchmultz/pi` tree adds native persisted `context_window` entries and `newContext`, provider-request preflight, the `session_before_auto_compact` extension hook, and context-usage/compaction-settings APIs; fork tests cover rollover before a request, after oversized tool results, overflow retry, persistence failure, and resume ([fork session tests](https://github.com/fitchmultz/pi/blob/main/packages/coding-agent/test/suite/agent-session-before-auto-compact.test.ts), [new-context tests](https://github.com/fitchmultz/pi/blob/main/packages/coding-agent/test/suite/agent-session-prompt.test.ts)). These APIs do not appear in the corresponding upstream `0.85.1` export. They are fork primitives, not recent official-Pi lane functionality.

Posthorse `0.4.4` is the policy layer over those primitives. It keeps the persisted JSONL transcript complete and append-only while a `context_window` boundary removes the old window from **active model context**; then it supplies stable guidance, at most one best-effort checkpoint reminder, `new_context`, remaining-context estimates, bounded no-summary rollover/recovery records, durable notes, and window-aware history ([design](https://github.com/fitchmultz/pi-posthorse/blob/main/README.md#how-it-works), [implementation](https://github.com/fitchmultz/pi-posthorse/blob/main/index.ts)). Its integration tests exercise oversized text/image tool results, preflight and overflow rollover, atomic tool-batch boundaries, resume, and history recovery ([tests](https://github.com/fitchmultz/pi-posthorse/blob/main/test/integration/posthorse-in-pi.test.ts)). Posthorse explicitly requires the fork; official unpatched Pi is unsupported. Its compatibility baseline is the fork commit above at Pi `0.85.0`, even though the inspected unidentifiable fork snapshot reports `0.85.1`.

## Recommendation for the pre-change Bun CLI

This assessment describes the code **before** the lane implementation. The
subsequent scope decision is recorded in
[ADR 0002](../adr/0002-explicit-lanes-and-context-windows.md).

Do not adopt Pi lanes, subprocess subagents, or Posthorse yet. The assessed CLI makes one fresh OpenRouter request, advertises `Read`, discards tool-call metadata, executes no tool, and has no continuation or retained context. The simplest next step is dependency-free: extend the provider-neutral response/message contract to carry validated tool calls, dispatch only the existing `Read` tool, append the assistant tool-call and tool-result messages in order, and request the next assistant turn until final text (with a small turn bound and tests). That establishes the minimum agent loop on which sessions, ownership, rollover, or delegation could later have useful semantics; importing a durable multi-lane runtime or maintaining the required Posthorse fork now would solve problems this CLI does not yet have.
